# Classroom review V2 implementation contract

User-approved scope: whole-class guide and semantic sections; concise knowledge explanation, applicable conditions and classroom focus; optional examples only when grounded; clickable transcript/photo indexes; complete ordered review scheme with a suggested date; mark reviewed removes the pending task while preserving material. No quiz, complex scheduling or live QA required. Preserve QA scope identities for later integration.

POST `/v2/study/review`: `{stage: "outline" | "unit" | "plan", input: <below>, outline?: <outline>, topicId?: string, units?: [<unit>]}`. JSON replies are the stage object, not an envelope. Authentication uses optional proxy access token, never provider key in Android. Provider capacity/truncation errors are explicit, no silent omission or application content cap.

Input wire fields: `schemaVersion:2, sessionId` (opaque classroom identity), `sourceHash`, `language:zh|en`, `title:string|null`, `today:YYYY-MM-DD`, `course` (nullable course card with id/revision/name/background/goals/chapters/terminology/prerequisites/sources), `sources:[{id,sessionId,segmentId,startMs,endMs,text,isCurrent}]`, `photos:[{id,sessionId,atMs}]`, `notes:[{id,atMs,kind,text}]`. No image bytes/paths/audio. History sources are explicitly consented same-course classroom originals. Current sources must be fully covered by outline sections. Photo indexes express temporal relevance, not image understanding. Equal-time source IDs use ordinal character ordering on both platforms.

Outline: `{overview:string, sections:[{id,title,sourceIds:[string]}], topics:[{id,title,sectionIds:[string],sourceIds:[string]}]}`. Sections partition all current source IDs in chronological order without omissions/duplicates. A topic may reference multiple sections; all sections must have topics. Topics aggregate repeated concepts; topic sourceIds belong to its sections. IDs must be unique, nonempty, and all references must resolve. No empty overview/sections/topics.

Provider-only outline protocol: each batch sends every complete current source with a zero-based `index` and the inclusive final index. The model returns sections with `startIndex/endIndex` and topics with `sectionIds`. The server requires integer, contiguous, nonoverlapping ranges from zero through the final source, then maps them to original IDs. It derives topic sources from explicitly selected validated sections. Missing coverage, invalid ranges and mixed range/ID sections are rejected rather than repaired. Cross-batch synthesis receives compact section identities/titles and must cover all sections. The Android wire format above remains unchanged; legacy ID responses still require strict original coverage validation.

Unit: `{id:topicId,title,explanation,conditions:string,classroomFocus:string,example:string|null,sourceIds:[string],photoIds:[string],sectionIds:[string]}`. Explanation and classroomFocus required; conditions can be empty when not applicable. Sources include at least one current source from the topic plus optional history references. Referenced photos must exist in input. SectionIds equal this topic's sectionIds. Do not invent examples; no mandatory confusion points or long evidence quotes.

Plan: `{title,introduction,suggestedDate:YYYY-MM-DD,steps:[{title,instruction,unitIds:[string]}]}`. Each unit must appear in at least one step; no unknown/empty unit refs. Suggested date >= input.today; generation date anchors date interpretation. Ordered steps must allow students to review the whole class. No budget/importance/quiz fields. Reviewed state is local, never generated by the model.

Android public API in `com.classmemory.app.review` (new files; V1 left intact):
- `ReviewSource(id,sessionId,segmentId,startMs,endMs,text,isCurrent)`
- `ReviewPhotoRef(id,sessionId,atMs)`
- `ReviewNote(id,atMs,kind,text)`
- `ReviewInput(sessionId,sourceHash,language,title,today,course:CourseContext?,sources:List<ReviewSource>,photos:List<ReviewPhotoRef>,notes:List<ReviewNote>)`
- `ReviewSection(id,title,sourceIds)`, `ReviewTopic(id,title,sectionIds,sourceIds)`, `ReviewOutline(overview,sections,topics)`
- `ReviewUnit(id,title,explanation,conditions,classroomFocus,example:String?,sourceIds,photoIds,sectionIds)`
- `ReviewStep(title,instruction,unitIds)`, `ReviewPlan(title,introduction,suggestedDate,steps)`
- `ReviewRun(input,outline:ReviewOutline?=null,units:Map<String,ReviewUnit>=emptyMap(),plan:ReviewPlan?=null,errors:Map<String,String>=emptyMap(),reviewedAt:Long?=null,updatedAt:Long)`
- `ReviewStore(File(directory))`: suspend `latest(sessionId):ReviewRun?`, `allLatest():List<ReviewRun>`, `save(run)`, `markReviewed(sessionId,sourceHash)`, `deleteSession(sessionId)`; retains per-sourceHash historical runs until the owning classroom is deleted; `changes:StateFlow<Long>` for UI refresh. Validates paths, atomic writes, never silently resets corrupt data.
- `ReviewGateway` suspend `outline(input)`, `unit(input,outline,topicId)`, `plan(input,outline,units:List<ReviewUnit>)`.
- `ReviewHttpGateway(baseUrl,accessToken:String="")` HTTPS and optional auth, cancellable requests, explicit provider errors, no content byte cap.
- `ReviewCoordinator(store,gateway,currentHash:suspend(String)->String?)`: suspend `run(input,onProgress:(String)->Unit={ }):ReviewRun`; persists successful outline/units/plan, skips valid existing stages on retry, preserves failed units and errors; checks current hash/deletion before and after calls and before final success. A missing/deleted/stale source throws; partial successes remain. Errors use stage keys `outline`, `unit:<id>`, `plan`. No infinite/automatic retry.
- `ReviewQaScope(sessionId,sourceHash,sectionId:String?=null)` reserved identity; sectionId null means whole class.

Repository assembles the current class and earlier same-course originals in a consistent Room snapshot. Input hashing runs off the UI thread. `ReviewRuntime` owns process-lifetime requests so navigating to an index does not cancel a running analysis; checkpoints support explicit retry after process termination. Service configuration lives in private preferences; provider credentials remain outside the app.

## V3 independent contract

`POST /v3/study/review` requires `input.schemaVersion: 3`; the V2 route and stored V2 results remain supported. V3 uses the same input metadata and outline structure as V2. Photos carry only `id`, `sessionId`, and `atMs`; they are local time indexes, and no image pixels are sent or interpreted.

Unit retains V2 fields and adds `markdown`, a coherent learning explanation with formulas, derivations, classroom examples, conditions and focus when appropriate. Internally preserve source IDs; Android shows the earliest current source reference. Notes are student questions/comments, not teacher quotations. Plan steps use `{title,task,completionCriteria,unitIds}`; Android persists per-step check state locally. V3 cached results must be distinguished from V2; V2 results remain readable.
